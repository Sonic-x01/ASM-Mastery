نقل البيانات: mov وعيلتها

ثلث أي برنامج حقيقي mov. بس الـ mov فيها قواعد وحدود (حجم الأرقام، الـ extension، الذاكرة)، ونسخ تانية (movzx، movsx، movsxd، xchg، bswap) كل واحدة بتقولك معلومة عن الكود الأصلي. المرحلة دي هتخليك تقرا أي نقل بيانات من نظرة.

mov: الأشكال المسموحة copy, not move

اسمها "move" بس هي في الحقيقة نسخ: المصدر بيفضل زي ما هو. وmov مبتغيرش الـ flags أبدًا.

حدود الـ immediate: لغز الـ 64-bit imm32 sign-extended

في x86-64، أغلب الـ instructions مبتقبلش رقم ثابت أكبر من 32-bit. لو العملية 64-bit، الرقم الـ 32-bit بيتعمله sign-extension لـ 64. الاستثناء الوحيد: mov r64, imm64 (اسمها في GAS/objdump movabs) — 10 bytes كاملة.

اعرف الثوابت من الـ bytes

جرّب الـ instructions دي في مستكشف الـ encoding (المرحلة 19) أو اضغط ⚙ Bytes على أي مثال. لما تشوف في x64dbg 48 B8 + 8 bytes، ده غالبًا pointer أو ثابت كبير — وفي الـ malware كتير بيبقى stack string أو مفتاح تشفير أو hash.

التكبير: movzx وmovsx وmovsxd widening

Instructionالأشكاليعني في C
movzxr16/32/64 ← r/m8، r32/64 ← r/m16cast من unsigned char / unsigned short
movsxنفس الأشكالcast من char / short (signed)
movsxdr64 ← r/m32cast من int لـ long/size_t/pointer offset
mov r32, r/m32—cast من unsigned int لـ 64-bit (مفيش movzx r64, r32 لأن الـ mov بتصفّر أصلًا)

شوف الـ compiler بيعمل إيه مع دالة بتجمع 5 أنواع مختلفة في long. على Linux (gcc) هتلاقي كل نوع ليه instruction بتفضحه. وعلى Windows (MSVC) لاحظ حاجتين: الحسابات كلها 32-bit (لأن long = 4 bytes في LLP64!)، والـ argument الخامس بيتقرا من الـ stack (ui$[rsp]) لأن Windows بيحط أول 4 بس في registers:

long widen(char c, unsigned char u, short s, int i, unsigned int ui) { long r = c; r += u; r += s; r += i; r += ui; return r; }
🔬
استرجاع الأنواع من gcc -O2 فوق

movsx rdi, dil ⇐ الـ arg الأول char signed. movzx esi, sil ⇐ التاني unsigned char. movsx rdx, dx ⇐ short. movsx rcx, ecx (= movsxd) ⇐ int. mov r8d, r8d ⇐ unsigned int (zero-extend). والنتيجة في rax كامل ⇐ النوع الراجع 64-bit. ده بالظبط إزاي الـ decompiler بيخمّن الأنواع — وإنت دلوقتي تقدر تتأكد منه.

نسخ الذاكرة: struct copy و swap real compilers

struct point { long x, y, z; }; void copy_point(struct point *dst, const struct point *src) { *dst = *src; } void swap(long *a, long *b) { long t = *a; *a = *b; *b = t; }

لاحظ إن مفيش "متغير t" في الـ assembly — الـ compiler استخدم registers. الأسماء والمتغيرات المؤقتة بتختفي، والـ reverser بيرجّعها من شكل حركة البيانات.

xchg: تبديل في خطوة واحدة atomic with memory

xchg a, b بتبدّل القيمتين. لو واحد منهم في الذاكرة، الـ CPU بيعملها atomic أوتوماتيك (كأن قبلها lock) — عشان كده بتشوفها في الـ spinlocks والـ mutexes، وبطيئة نسبيًا. وحقيقة لطيفة: nop (0x90) أصلًا هي xchg eax, eax القديمة! والـ NOP sleds في الـ exploits = سلسلة 90 90 90….

section .data a: dq 0xAAAA b: dq 0xBBBB section .text swaps: ; 1) registers with a temporary mov rcx, rax mov rax, rbx mov rbx, rcx ; 2) registers with xchg (no temporary) xchg rax, rbx ; 3) two memory qwords: must go through registers mov rdx, [rel a] xchg rdx, [rel b] ; atomic swap with memory mov [rel a], rdx ret

bswap: قلب الـ endianness network byte order

bswap eax بتعكس ترتيب الـ 4 bytes: 0x12345678 ← 0x78563412. ده بالظبط htonl/ntohl: الـ network بيستخدم big-endian. الـ malware اللي بيكلّم C2 بيبني الـ IP والـ port بالشكل ده، وأحيانًا بيخبّي الـ IP كرقم في الكود — لو شفت mov ecx, 0x0100007F وبعدها bswap أو htonl… اقرا الـ bytes: 7F 00 00 01 = 127.0.0.1.

unsigned int to_big_endian(unsigned int x) { return __builtin_bswap32(x); } unsigned short port_to_network(unsigned short port) { return (unsigned short)((port << 8) | (port >> 8)); }

في الدالة التانية، الـ compiler فهم إن الـ shifts دي = تبديل bytes لـ 16-bit واستخدم rol ax, 8 (rotate) — هنشرح الـ rotate في مرحلة الـ bits.

push وpop: لمحة تفاصيل في المرحلة 10

push rax = rsp -= 8 ثم [rsp] = rax. وpop rbx = rbx = [rsp] ثم rsp += 8. في 64-bit الـ push/pop دايمًا 8 bytes (أو 2 نادرًا)، وpush eax مش موجودة. والـ push imm بتاخد imm32 وبتعمله sign-extend لـ 64-bit. الحيلة الكلاسيكية: push 41h + pop rax = طريقة لتحميل رقم صغير بـ 3 bytes بس (6A 41 58) — بتشوفها في الـ shellcode اللي عايز يبقى صغير ومن غير null bytes.
