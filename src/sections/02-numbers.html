الأرقام وتمثيل البيانات: إزاي الـ CPU شايف كل حاجة

في الذاكرة مفيش "رقم سالب" ولا "حرف" ولا "عنوان" — فيه bits بس. نفس الـ 4 bytes ممكن تكون رقم موجب، أو سالب، أو 4 حروف، أو float، أو pointer — المعنى بييجي من الـ instruction اللي بتستخدمها. المرحلة دي هي اللي هتخليك تبص على hexdump وتشوف معنى.

ليه Hex؟ 1 hex digit = 4 bits

الـ binary طويل جدًا للبني آدمين، والـ decimal مش بيتقسم على حدود الـ bits. الـ hexadecimal (أساس 16) هو الحل: كل رقم hex = 4 bits بالظبط (nibble)، وكل byte = رقمين hex. عشان كده كل الأدوات (x64dbg، IDA، hex editors) بتتكلم hex.

التحويل بين hex وbinary مجرد استبدال كل nibble: 0xB7 = 1011 0111. ولـ decimal: 0xB7 = 11×16 + 7 = 183. والعكس: اقسم على 16 وخد البواقي. احفظ القيم دي لأنك هتشوفها كل يوم: 0xFF = 255، 0x100 = 256، 0x7F = 127، 0x80 = 128، 0x400 = 1024، 0x1000 = 4096 (حجم الـ page)، 0xFFFF = 65535.

🔬
Windows ≠ Linux في حجم long

Windows x64 بيستخدم نموذج LLP64: long = 4 bytes. Linux بيستخدم LP64: long = 8 bytes. والـ wchar_t = 2 bytes على Windows (UTF-16) و4 على Linux. لما تعمل struct recovery لـ malware بتاع Windows افتكر ده. وليه "word" = 16 bit حتى على 64-bit؟ لأن Intel سمّت الأحجام أيام الـ 8086 وفضلت ثابتة.

الأرقام السالبة: Two's Complement أهم فكرة في المرحلة

الـ CPU بيمثل السالب بطريقة اسمها two's complement: عشان تجيب −x، اقلب كل الـ bits وزوّد 1. مثال بـ 8 bits:

−5 في byte واحد
50000 0101الرقم الموجب = 0x05
NOT1111 1010اقلب كل الـ bits = 0xFA
+11111 1011زوّد 1 = 0xFB = −5 ✓
جرّب في المحوّل اللي فوق: اكتب -5 واختار 8-bit — هتلاقي 0xFB.

ليه الطريقة دي عبقرية؟ لأن نفس دائرة الجمع بتشتغل للـ signed والـ unsigned: 0xFB + 0x05 = 0x100، والـ byte مبيشيلش غير 8 bits فالنتيجة 0x00 = صفر ✓. الـ CPU مبيعرفش الرقم signed ولا unsigned — هو بيجمع bits وخلاص، وإنت (والـ instructions اللي بعدها) اللي بتفسّر.

🔑

قواعد تحفظها

−1 = كل الـ bits بواحد: 0xFF / 0xFFFF / 0xFFFFFFFF / 0xFFFFFFFFFFFFFFFF. أعلى bit = 1 ⇐ سالب (لو signed). أصغر سالب: 0x80…00، وماعندوش موجب مقابل له (−(−128) في byte = −128 تاني!).

🕵️

في الـ disassembly

لما تشوف cmp eax, 0FFFFFFFFh فده eax == -1. وadd rsp, 0FFFFFFFFFFFFFFF0h = sub rsp, 16. وand rsp, 0FFFFFFFFFFFFFFF0h = "قرّب rsp لمضاعف 16". IDA أحيانًا بيعرض السالب كـ hex كبير — اضغط - عليه عشان يقلبه.

التكبير: Sign Extension و Zero Extension movsx / movzx

لما تنقل رقم صغير لمكان أكبر (byte → dword مثلًا)، لازم تقرر تملا الـ bits الجديدة بإيه:

bytezero-extend → dword (unsigned)sign-extend → dword (signed)
0x05 (5)0x00000005 = 50x00000005 = 5
0xF0 (240 أو −16)0x000000F0 = 2400xFFFFFFF0 = −16
0x80 (128 أو −128)0x00000080 = 1280xFFFFFF80 = −128

Zero-extension بتملا أصفار، وsign-extension بتنسخ أعلى bit في كل الخانات الجديدة. الـ compiler بيختار حسب النوع في C: unsigned char ← movzx، char (signed) ← movsx. يعني لما تشوف movsx في الـ disassembly تعرف إن المتغير الأصلي signed — معلومة ذهبية في استرجاع الأنواع. جرّبها في المعمل:

extend: mov al, 0xF0 ; al = 1111 0000 movzx ebx, al ; zero-extend: ebx = 0x000000F0 (240) movsx ecx, al ; sign-extend: ecx = 0xFFFFFFF0 (-16) movsx rdx, al ; sign-extend to 64-bit mov al, 0x70 ; top bit is 0 this time movsx esi, al ; = 0x00000070, same as movzx ret

Endianness: ليه الأرقام بتبان مقلوبة little-endian

لما رقم أكبر من byte يتخزن في الذاكرة، لازم الـ bytes بتاعته تترتب بترتيب ما. x86 بيستخدم little-endian: الـ byte الأصغر (least significant) في العنوان الأصغر. فالـ dword 0x12345678 بيتخزن كده:

00403000 78 56 34 12 xV4. ↑ الـ byte ده = 0x78 = أصغر جزء من الرقم

وده بيأثر على كل حاجة: قراية الـ hexdumps، الـ machine code (mov eax, 0x12345678 = B8 78 56 34 12)، الـ shellcode، والـ network (اللي بيستخدم big-endian — عشان كده الـ malware بيستخدم htons/htonl أو bswap قبل ما يبعت port أو IP). جرّب:

💡
Stack strings

الـ malware كتير بيبني strings على الـ stack عشان أداة strings متلاقيهاش: mov rax, 6578652E646D63h ثم mov [rsp+20h], rax. اقرا الـ bytes من اليمين للشمال: 63 6D 64 2E 65 78 65 = "cmd.exe". بسبب الـ little-endian، الـ string بتبان مقلوبة جوه الرقم.

لمحة: الأرقام العشرية (float/double) IEEE-754

الـ floats مش two's complement — ليها شكل تاني (IEEE-754): sign + exponent + mantissa. مش محتاج تحسبها بإيدك، بس محتاج تعرف شكلها لما تشوفها كثوابت في الـ binary:

القيمةfloat (32-bit)double (64-bit)
1.00x3F8000000x3FF0000000000000
−1.00xBF8000000xBFF0000000000000
0.50x3F0000000x3FE0000000000000
2.00x400000000x4000000000000000

لو شفت mov eax, 3F800000h جنب movd xmm0, eax — ده 1.0f. وأي dword بيبدأ بـ 3F أو 40 أو BF أو C0 وجاي من xmm غالبًا float. التفاصيل في مرحلة الـ SIMD.

✏️ تمارين المرحلة 02

0x2F بالـ decimal = ؟ 29 45 47 215 2×16 + 15 = 47. الخانة اليمين × 1، والشمال × 16. و F = 15. إيه تمثيل −3 في byte (two's complement)؟ 0x83 0xFD 0xFC 0x03 3 = 0000 0011 → اقلب = 1111 1100 → +1 = 1111 1101 = 0xFD. (0x83 ده طريقة "sign-magnitude" اللي الـ CPU مش بيستخدمها.) اقلب كل bits الـ 3 وبعدين زوّد 1. الـ byte 0x9C لو اتفسّر signed قيمته كام؟ 156 −28 −156 −100 0x9C = 156 unsigned. أعلى bit = 1 فهو سالب: 156 − 256 = −100. القاعدة السريعة: لو أعلى bit = 1، القيمة signed = unsigned − 2ⁿ (هنا n = 8). الـ dword 0xCAFEBABE متخزن في الذاكرة عند 0x1000 على x86. الـ byte عند 0x1000 بالظبط = ؟ 0xBE 0xCA 0xBA 0xFE little-endian: الأصغر الأول. الترتيب في الذاكرة: BE BA FE CA. x86 little-endian: آخر byte في الرقم (الأصغر) بيتخزن أول. byte قيمته 0xF6 اتعمله movsx لـ dword. النتيجة؟ 0x000000F6 0xF6000000 0xFFFFFFF6 0x0000FFF6 أعلى bit في 0xF6 = 1، فالـ sign extension بتملا الـ 24 bit الجديدة بواحد: 0xFFFFFFF6 = −10. movsx بتنسخ أعلى bit. أعلى bit في 0xF6 كام؟ في binary بتاع Windows x64، struct فيها long وlong long و pointer. أحجامهم بالترتيب؟ 8، 8، 8 4، 8، 8 4، 4، 8 8، 16، 8 LLP64: long = 4 bytes، long long = 8، الـ pointer = 8. على Linux الـ long بيبقى 8. Windows بيستخدم LLP64 — الـ long فضل 32-bit. شفت في hexdump: 68 00 74 00 74 00 70 00. ده غالبًا إيه؟ أرقام 16-bit عشوائية machine code ASCII string "h.t.t.p." UTF-16LE (wide) string = L"http" حرف ثم صفر = wide string بتاع Windows. 68 74 74 70 = "http". غالبًا URL للـ C2! بص على النمط: byte قيمته حرف، وبعده 00، وهكذا. الفرق بين 'a' و'A' في ASCII؟ 0x20 (bit رقم 5 بس) 0x10 0x26 مفيش علاقة ثابتة 0x61 − 0x41 = 0x20. عشان كده xor al, 20h بيقلب حالة الحرف، وبعض الـ malware بيعمل hashing لأسماء الـ APIs بعد ما يحوّلها لـ uppercase بـ and al, 0DFh. 'A' = 0x41 و 'a' = 0x61. شفت mov dword ptr [rbp-4], 3F800000h. أغلب الظن إن المتغير ده: pointer int قيمته مليار float قيمته 1.0 string 0x3F800000 هو تمثيل 1.0f في IEEE-754. احفظ الشكل ده. بص على جدول IEEE-754 في المرحلة. أكبر قيمة signed في dword؟ 0xFFFFFFFF 0x7FFFFFFF 0x80000000 0x7FFFFFFE 0x7FFFFFFF = 2,147,483,647. واحد زيادة = 0x80000000 = أصغر سالب (−2,147,483,648) — ده الـ signed overflow. أعلى bit لازم يبقى 0 عشان الرقم يفضل موجب. وأنت بتحلل sample، لقيت في الـ .data الـ 4 bytes دول عند الـ offset بتاع متغير اسمه magic (نوعه dword): 0D F0 AD 0B. إيه قيمة magic بالـ hex؟ little-endian: أول byte في الذاكرة هو آخر byte في الرقم. اعكس ترتيب الـ bytes: 0B AD F0 0D = 0x0BADF00D ("bad food" — magic numbers زي دي بتتحط عشان تتعرف بسهولة في الذاكرة). الـ malware فيه السطر ده: mov rax, 6578652E646D63h وبعده بيخزّن rax على الـ stack ويعامله كـ string. إيه الـ string؟ اكتب الـ bytes بترتيب الذاكرة (من الأصغر)، وحوّل كل byte لحرف ASCII. في الذاكرة: 63 6D 64 2E 65 78 65 00 = c m d . e x e \0 = "cmd.exe". الـ byte الأعلى (الثامن) = 00 بيعمل الـ NUL terminator ببلاش. الـ wide string L"KILL" متخزنة عند 0x5000. إيه قيمة الـ byte عند العنوان 0x5004؟ ('A' = 0x41، فـ 'I' = 0x49 و'K' = 0x4B و'L' = 0x4C) كل حرف = 2 bytes: الحرف نفسه وبعده 0x00. ارسم الجدول: العنوان ← الـ byte. 0x5000=4B ('K')، 0x5001=00، 0x5002=49 ('I')، 0x5003=00، 0x5004=4C ('L')، 0x5005=00… الحرف رقم n (من صفر) بيبدأ عند base + 2n — وده نفس الحساب اللي هتشوفه في الـ disassembly: movzx eax, word ptr [rcx+rdx*2]. عندك buffer فاضي اسمه buf في الـ .data. اكتب instruction واحدة (+ ret) تخلي الـ bytes في buf = "ABCD" بالظبط — يعني buf[0]='A'… استخدم mov dword [rel buf], ... وفكّر في الـ little-endian.
