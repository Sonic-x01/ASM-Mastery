المرحلة الرابعة · خريطة الـ process

الذاكرة والعناوين: فين كل حاجة، وإزاي توصلها

أي instruction بتلمس الذاكرة فيها [ … ]. لو فهمت إيه اللي جوه الأقواس وإزاي بيتحسب، هتقدر تشوف في [rbx+rcx*8+10h] إنها obj->items[i]. والأهم: هتفهم الخريطة اللي الـ process عايش فيها — الكود فين، الـ stack فين، والـ malware بيحقن نفسه فين.

الـ Virtual Memory: كل process فاكر نفسه لوحده paging

العنوان اللي بتشوفه في الـ debugger (زي 0x401000) مش مكان حقيقي في الـ RAM. ده عنوان افتراضي (virtual). الـ CPU (بوحدة اسمها MMU) بيترجمه لعنوان فعلي باستخدام جدول pages خاص بكل process. الذاكرة متقسمة لـ pages كل واحدة 4 KB (0x1000 byte)، وكل page ليها صلاحيات.

📏

48-bit بس

الـ pointer 64-bit، بس المعالج بيستخدم 48 bit (أو 57 مع paging خماسي). الـ user space على Linux وWindows من 0 لحد 0x00007FFFFFFFFFFF، والـ kernel في النص العالي 0xFFFF8000….

🚫

Canonical addresses

الـ bits من 47 لـ 63 لازم كلها زي bit 47. عنوان زي 0x0000800000000000 "non-canonical" ← أي وصول ليه = crash فوري. (بتشوفه في exploits فاشلة.)

🕳️

Null page

أول 64 KB من الذاكرة مش متعملها map على Windows وLinux، عشان أي NULL pointer dereference يعمل crash بدل ما يقرا زبالة.

البرامج الطبيعية نادرًا ما بتحتاج ذاكرة writable وexecutable في نفس الوقت. لما تشوف VirtualAlloc(…, 0x40) (PAGE_EXECUTE_READWRITE = 0x40) أو VirtualProtect بيحوّل ذاكرة لـ executable، أو mprotect(…, PROT_READ|PROT_WRITE|PROT_EXEC) = 7 على Linux، غالبًا الـ malware بيفك تشفير payload ويستعد ينفّذه. حط breakpoint بعدها وdump الذاكرة دي.

جرّب بنفسك: الكود ده بيحاول يكتب في string موجودة في .rodata. المعمل هيعمل crash زي الـ CPU الحقيقي بالظبط:

section .rodata msg: db "constant", 0 section .text crash: lea rax, [rel msg] ; rax = address of the string (fine) mov bl, [rax] ; reading is allowed -> bl = 'c' mov byte [rax], 'C' ; writing to r-- page -> SEGFAULT ret

الـ Memory Operand: [base + index×scale + disp] addressing modes

أي وصول للذاكرة في x86-64 عنوانه بيتحسب بالمعادلة دي (كل جزء اختياري):

effective address = base + index × scale + displacement
baseأي register 64-bitبداية الحاجة (pointer لـ array أو struct أو rbp/rsp)
indexأي register ما عدا rspرقم العنصر (i)
scale1 أو 2 أو 4 أو 8 بسحجم العنصر: char / short / int / pointer
dispرقم ثابت (signed، لحد 32-bit)offset الـ field، أو مكان المتغير على الـ stack
الشكلمعناه في Cهتشوفه فين

حجم الوصول: byte / word / dword / qword size specifiers

العنوان بيقول "فين"، بس مش بيقول "قد إيه". الحجم بييجي من الـ register التاني: mov eax, [rbx] بتقرا 4 bytes لأن eax 32-bit. لو مفيش register (زي mov [rbx], 5) لازم تقول الحجم صراحة:

NASM (الكورس)IDA / MASM / x64dbggdb / objdump (AT&T)
mov dword [rbx], 5mov dword ptr [rbx], 5movl $5, (%rbx)
movzx eax, byte [rdi+rcx]movzx eax, byte ptr [rdi+rcx]movzbl (%rdi,%rcx), %eax
mov rax, [rel counter]mov rax, cs:counter (IDA) / qword ptr [rip+…]mov counter(%rip), %rax

المعمل بتاعنا بيقبل الشكلين (dword وdword ptr) عشان تقدر تنسخ من IDA أو x64dbg مباشرة.

RIP-relative: إزاي الكود الحديث بيوصل للـ globals [rel label]

في x64، الطريقة الطبيعية للوصول لمتغير global هي نسبةً لـ RIP: الـ instruction بتخزّن المسافة من نهايتها للمتغير، مش العنوان نفسه. ده بيخلي الكود يشتغل في أي مكان يتحمّل فيه (ضروري مع ASLR، وده اللي بيخلي الـ shellcode الحديث position-independent بسهولة).

default rel ; make [label] mean [rel label] section .data counter: dq 41 section .text global _start _start: mov rax, [counter] ; RIP-relative read (48 8B 05 + disp32) add rax, 1 mov [counter], rax ; RIP-relative write mov rdi, [counter] call print_int ; 42 call print_nl lea rdi, [counter] ; the ADDRESS itself (no memory read) call print_hex call print_nl xor edi, edi call exit

اضغط ⚙ Bytes: هتلاقي mov rax, [counter] = 48 8B 05 xx xx xx xx. الـ 4 bytes الأخيرة = counter − (عنوان الـ instruction اللي بعدها). الـ disassembler بيحسبها لك ويكتب [rip+0x2FF9] وجنبها اسم المتغير. في IDA هتشوفها mov rax, cs:counter.

⚠️
NASM: متنساش default rel

من غير default rel (أو [rel x])، NASM بيستخدم عنوان مطلق 32-bit (8B 04 25 …) — بيشتغل في برامجنا البسيطة، بس بيفشل في أي برنامج PIE أو DLL. NASM 3 بقى بيطلع warning عن كده. عوّد نفسك تكتبها في أول كل ملف.

lea: احسب العنوان من غير ما تلمس الذاكرة load effective address

mov rax, [rbx+8] = "روح للعنوان rbx+8 وهات اللي فيه". lea rax, [rbx+8] = "احسب rbx+8 وحطّه في rax" — من غير أي وصول للذاكرة. ولأن المعادلة base + index×scale + disp فيها جمع وضرب، الـ compilers بيستخدموا lea كآلة حاسبة سريعة:

Instructionالمعنى
lea rax, [rdi+rsi]rax = a + b (من غير ما يغيّر الـ flags ومن غير ما يبوّظ a أو b)
lea eax, [rdi+rdi*2]eax = x * 3
lea eax, [rdi+rdi*4]eax = x * 5
lea eax, [rdi*8+7]eax = x*8 + 7
lea rcx, [rbp-40h]rcx = &local_buffer (هتشوفها قبل أي call بياخد pointer لمتغير محلي)
section .data arr: dd 10, 20, 30, 40, 50 ; int arr[5] section .text demo: ; rdi = i = 3 lea rbx, [rel arr] ; rbx = &arr[0] (address) mov eax, [rbx] ; eax = arr[0] = 10 (memory read) mov ecx, [rbx+8] ; ecx = arr[2] = 30 (disp = 2*4) mov edx, [rbx+rdi*4] ; edx = arr[i] = arr[3] = 40 lea rsi, [rbx+rdi*4] ; rsi = &arr[3] (no read!) lea r8, [rdi+rdi*4] ; r8 = i*5 = 15 (lea as math) lea r9, [rdi*8+7] ; r9 = i*8+7 = 31 ret
🎯
مفيش memory ← memory

x86 مبيسمحش بـ instruction فيها الاتنين memory: mov [rax], [rbx] غلط. لازم تعدّي على register: mov rcx, [rbx] ثم mov [rax], rcx. (الاستثناء الوحيد: الـ string instructions زي movsb — مرحلة 12.)

الـ Alignment ليه offsets بتبقى مضاعفات 8

الـ CPU أسرع لما قيمة حجمها N تكون في عنوان بيقبل القسمة على N (dword على 4، qword على 8). الـ compilers بيضيفوا padding في الـ structs عشان كده، والـ ABI بيطلب الـ stack يبقى aligned على 16 قبل أي call (هنشوف ليه في مرحلة الـ stack). وبعض الـ SSE instructions (زي movaps) بتعمل crash لو العنوان مش aligned على 16 — من أشهر أسباب الـ crashes لما تكتب Assembly بتنادي دوال C.

✏️ تمارين المرحلة 04

rbx = 0x1000 وrcx = 3. العنوان اللي [rbx+rcx*8+0x10] بيشاور عليه؟ 0x1013 0x1028 0x1038 0x1040 0x1000 + 3×8 + 0x10 = 0x1000 + 0x18 + 0x10 = 0x1028. جرّبها في حاسبة العنوان فوق. 3×8 = 24 = 0x18 (مش 0x24!). وبعدين زوّد 0x10. إيه الفرق بين mov rax, [rbx] وlea rax, [rbx]؟ مفيش فرق mov بتقرا الـ 8 bytes اللي عند العنوان، وlea بتحط العنوان نفسه (= rbx) lea أبطأ lea بتكتب في الذاكرة lea = Load Effective Address: بتحسب العنوان بس. يعني lea rax, [rbx] = mov rax, rbx. واحدة فيهم مبتلمسش الذاكرة خالص. شفت lea eax, [rcx+rcx*4] ثم add eax, eax. ده بيحسب إيه بـ x = ecx؟ x + 4 x * 5 x * 8 x * 10 x + 4x = 5x، وبعدين ×2 = 10x. الـ compilers بيعملوا كده بدل imul عشان أسرع. احسب lea الأول (x + 4x)، وبعدين الـ add بتضاعف. الـ disassembly فيه mov eax, dword ptr [rdi+rcx*4] جوه loop بتزوّد rcx. أغلب الظن: loop على array من int (4 bytes)، rdi = بداية الـ array، rcx = index loop على string (chars) array من pointers قراية struct field scale = 4 = حجم int، والـ index بيزيد ← arr[i]. الـ scale بيقولك حجم العنصر. أنهي instruction غلط ومش هتتعمل assemble؟ mov eax, [rbx+rcx*4+8] lea rax, [rax+rax*2] mov [rax], [rbx] mov dword [rsp+8], 0 memory ← memory مش مسموح في instruction واحدة. دوّر على الـ instruction اللي فيها الـ 2 operands في الذاكرة. process بيعمل VirtualAlloc بـ protection = 0x40، يكتب فيها bytes، ويعمل call عليها. ده غالبًا: تحميل DLL طبيعي بيفك/بينفّذ shellcode أو payload — 0x40 = PAGE_EXECUTE_READWRITE بيعمل allocate للـ stack بيقرا ملف RWX + كتابة + تنفيذ = النمط الكلاسيكي للـ loaders والـ shellcode runners. حط breakpoint على الـ call وdump الـ buffer. 0x40 = PAGE_EXECUTE_READWRITE. ليه برنامج يحتاج ذاكرة writable وexecutable؟ في x64، الـ instruction mov rax, [rip+0x1000] عند العنوان 0x401000 وطولها 7 bytes. بتقرا من؟ 0x401000 0x402000 0x401007 0x402007 RIP أثناء التنفيذ = العنوان اللي بعد الـ instruction = 0x401007. + 0x1000 = 0x402007. RIP-relative بيتحسب من نهاية الـ instruction. حجم الـ page القياسي على x86-64؟ 4 KB (0x1000) 512 byte 64 KB 1 MB 4096 byte. عشان كده العناوين الـ aligned على page بتنتهي بـ 3 أصفار hex (0x401000). (فيه كمان large pages: 2MB و1GB.) 0x1000 بالـ decimal كام؟ rdi = عنوان array من int (4 bytes)، rsi = i، rdx = j. رجّع في eax قيمة arr[i] + arr[j]. استخدم الـ addressing modes ([rdi+rsi*4]). pair_sum: xor eax, eax ret pair_sum: mov eax, [rdi+rsi*4] ; arr[i] add eax, [rdi+rdx*4] ; + arr[j] ret الـ input في rdi. رجّع x*9 + 4 في rax بـ instruction واحدة (+ ret). ممنوع imul/mul/shl. (تلميح: lea ومعادلة الـ addressing.) calc: mov rax, rdi ret calc: lea rax, [rdi+rdi*8+4] ; x + 8x + 4 ret الدالة دي بتاخد pointer لـ struct في rdi. الـ struct فيه array من pointers (كل واحد 8 bytes) بتبدأ عند offset 0x18. الدالة بترجع s->ptrs[i] — لأنهي i؟ get_item: mov rax, [rdi+0x40] ret offset = 0x18 + i×8. حل المعادلة: 0x40 = 0x18 + 8i. 0x40 − 0x18 = 0x28 = 40، و40 / 8 = 5 ⇐ s->ptrs[5]. لما تشوف offsets ثابتة بالشكل ده في دوال كتير، ابدأ ابني الـ struct في IDA/Ghidra (Structures window) وسمّي كل field — هنعمل ده بالتفصيل في مرحلة الـ structs.
