Anti-VM وAnti-Sandbox

🧬

الـ CPU نفسه

cpuid leaf 1 ← ecx bit 31 (hypervisor). leaf 0x40000000 ← vendor في ebx/ecx/edx: "VMwareVMware"، "VBoxVBoxVBox"، "Microsoft Hv"، "KVMKVMKVM". وVMware backdoor: in eax, dx مع eax = 'VMXh' وdx = 'VX' (5658h).

🧾

آثار في النظام

MAC بيبدأ بـ 00:0C:29/00:50:56 (VMware) أو 08:00:27 (VirtualBox)، processes (vmtoolsd.exe، VBoxService.exe)، registry keys، ملفات drivers، أسماء أجهزة.

📉

موارد قليلة = sandbox

أقل من 2 CPU، RAM أقل من 4GB، disk صغير، uptime قصير، مفيش ملفات حديثة، مفيش حركة ماوس. هتشوف GlobalMemoryStatusEx، GetSystemInfo، GetCursorPos مرتين.

⏳

استنى الـ sandbox يزهق

Sleep(600000) (الـ sandboxes بتسرّع الـ Sleep — فبيقيس الوقت قبل وبعد بـ rdtsc/GetTickCount عشان يكتشف التسريع)، أو loops حسابية طويلة جدًا.

Obfuscation: الكود اللي اتعمل عشان يتوّهك

🎲

Opaque predicates

شرط نتيجته معروفة مسبقًا بس صعب على الأداة تثبتها: x*(x+1) دايمًا زوجي، x² ≥ 0… الفرع التاني = زبالة عمرها ما تتنفذ.

🗑️

Junk code + MBA

instructions ملهاش تأثير (push/pop، xchg مرتين)، وتعبيرات Mixed Boolean-Arithmetic: (x ^ y) + 2*(x & y) = x + y.

🖥️

Virtualization

VMProtect/Themida بيحوّلوا الكود لـ bytecode لـ CPU وهمي، وinterpreter بيشغّله. هتشوف loop ضخمة فيها movzx لـ opcode وjump table. التحليل static هنا شبه مستحيل — اشتغل dynamic.

Unpacking ASM Explorer

💡
وصفة الـ unpacking العامة

(1) DIE: أي packer؟ لو UPX عادي ← upx -d. (2) breakpoints على VirtualAlloc/VirtualProtect/WriteProcessMemory/CreateProcessInternalW — كتير من الـ packers بيفكوا payload في ذاكرة جديدة أو process جديد. (3) لما الـ protection تتغير لـ executable أو تلاقي MZ في buffer جديد ← dump الـ buffer. (4) لو بيفك في نفسه: دوّر على الـ tail jump (أو ESP trick) ← OEP ← Scylla. (5) أدوات أوتوماتيك (unpac.me، mal_unpack) بتوفر وقت.

جوه الـ debugger الـ sample بيطلع رسالة «Update failed» ويقفل، وفي الـ sandbox بيعمل اتصالات network. أول احتمال؟ الـ sample بايظ anti-debug بيوديه لمسار مزيف لما يحس بالـ debugger الـ network مقفولة محتاج admin سلوك مختلف تحت الـ debugger = anti-debug. دوّر على الـ checks (أو شغّل ScyllaHide) قبل ما تحكم. ليه السلوك اختلف؟ rdtsc / mov esi, eax / … كود قصير … / rdtsc / sub eax, esi / cmp eax, 1000h / ja kill. ده: توليد رقم عشوائي قياس أداء عادي anti-VM بالـ cpuid timing check: لو الكود ده خد cycles كتير (عشان بتعمل single-step) ← debugger الحل: متعملش step جوه المنطقة دي (breakpoint بعدها وRun)، أو patch الـ ja. الفرق بين قراءتين للـ timestamp counter… بعد mov eax, 40000000h / cpuid، الـ sample بيقارن ebx بـ 61774D56h. بيدوّر على: VMware — "VMwa" (أول 4 حروف من "VMwareVMware") Intel Hyper-V debugger 0x61774D56 little-endian = 56 4D 77 61 = "VMwa". حوّل الـ dword لحروف (little-endian). IDA بيعرض function شكلها نجمة: block واحد في النص فيه switch على متغير، وكل الـ blocks بتكتب في المتغير ده وترجع له. ده: jump table عادي VM protector control-flow flattening — تتبّع قيم متغير الـ state عشان ترتّب الـ blocks exception handler VM protector بيبان شبهه بس فيه bytecode بيتقرا؛ الـ flattening الـ blocks نفسها كود x86 أصلي. شوف الـ diagram. rdi = pointer لـ PEB (x64). رجّع eax = 1 لو BeingDebugged (byte عند +0x02) ≠ 0 أو NtGlobalFlag (dword عند +0xBC) فيه أي bit من 0x70. وإلا 0. (ده اللي الـ malware بيعمله inline — واللي ScyllaHide بيصفّره.) is_debugged: xor eax, eax ret is_debugged: movzx eax, byte [rdi+2] ; PEB.BeingDebugged mov ecx, [rdi+0xBC] ; PEB.NtGlobalFlag and ecx, 0x70 ; FLG_HEAP_ENABLE_TAIL_CHECK | FREE_CHECK | VALIDATE_PARAMETERS or eax, ecx setnz al movzx eax, al ret نفّذ cpuid بـ eax = 1 ورجّع bit 31 من ecx (الـ hypervisor bit) في eax (0 أو 1). انتبه: cpuid بيكتب في ebx، وrbx callee-saved — الاختبارات بتتأكد إنه رجع زي ما كان. is_vm: mov eax, 1 cpuid xor eax, eax ret is_vm: push rbx ; cpuid clobbers ebx - and rbx is callee-saved mov eax, 1 cpuid mov eax, ecx shr eax, 31 ; hypervisor-present bit pop rbx ret الدالة دي flattened. أنهي قيمة لـ edi بترجّع 1؟ (تتبّع الـ state: كل block بيقولك مين اللي بعده.) check: mov eax, edi mov ecx, 0x3E2 ; initial state .dispatch: cmp ecx, 0x3E2 je .s_xor cmp ecx, 0x1B7 je .s_add cmp ecx, 0x9C4 je .s_mul cmp ecx, 0x7A1 je .s_cmp xor eax, eax ret .s_add: add eax, 7 mov ecx, 0x9C4 jmp .dispatch .s_cmp: cmp eax, 0x1F5 sete al movzx eax, al ret .s_xor: xor eax, 0x5A mov ecx, 0x1B7 jmp .dispatch .s_mul: lea eax, [rax+rax*2] mov ecx, 0x7A1 jmp .dispatch الترتيب: 0x3E2 (xor) ← 0x1B7 (add) ← 0x9C4 (mul) ← 0x7A1 (cmp). اعكس العمليات من 0x1F5. ((x ^ 0x5A) + 7) × 3 = 0x1F5 = 501 ← +7 = 167 ← x ^ 0x5A = 160 = 0xA0 ← x = 0xFA = 250. (وجرّبها في المعمل 🔬 بـ rdi=250.) كام input (من الـ 2³² قيمة) بيوصل لـ .fake؟ gate: mov eax, edi lea ecx, [rax+1] imul eax, ecx ; x * (x + 1) test al, 1 jnz .fake ; odd? mov eax, 1 ret .fake: ud2 ; junk the disassembler has to deal with x و x+1 واحد منهم زوجي دايمًا. 0: حاصل ضرب أي رقمين متتاليين زوجي (وده بيفضل صح حتى مع الـ overflow في 32-bit لأن أقل bit مبيتأثرش). الفرع .fake كود ميت اتحط عشان يلخبط الـ graph والـ decompiler — في IDA ممكن تعمل patch للـ jnz لـ NOP عشان الـ decompiler يشيله.
