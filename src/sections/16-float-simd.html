Floating Point وSIMD: الـ xmm في كل حتة

ممكن تفتكر إن الـ xmm registers للـ floats والألعاب بس. لكن في الـ reverse engineering بتشوفها في كل function تقريبًا: الـ compilers بيستخدموها عشان ينسخوا structs، ويصفّروا buffers، ويبنوا stack strings، ويعملوا vectorization لـ loops التشفير. والـ malware نفسه بيستخدم AES-NI. المرحلة دي هتخليك تقرا الكود ده من غير ما تتوه.

comisd ولا ucomisd؟

الاتنين بيطلعوا نفس الـ flags. الفرق: comisd بيرفع exception (invalid) لأي NaN، وucomisd للـ signaling NaN بس. الـ compilers بيستخدموا ucomisd لـ ==/!= وcomisd لـ < > <= >=. للـ reversing: اقراهم زي بعض.

x87: الـ FPU القديم 32-bit · shellcode

🥞

stack من 8 registers

st(0)…st(7)، 80-bit لكل واحد. fld بتعمل push، fstp بتعمل pop وتخزّن، fadd/fmul على st(0)، fild/fistp للـ integers. في الـ 32-bit (cdecl) الـ float/double بيرجع في st(0) — هتشوفها كتير في الـ malware الـ 32-bit.

🎯

حيلة الـ GetPC في الـ shellcode

fldz ثم fnstenv [esp-12] ثم pop ecx: الـ FPU بيحفظ عنوان آخر instruction x87 اتنفذت، فالـ shellcode بيعرف هو فين في الذاكرة. ده توقيع مشهور لـ encoders زي shikata_ga_nai. لو شفت fnstenv في بداية buffer ← shellcode متشفّر.

Stack strings بالـ xmm: string متشفرة جوه الكود

الـ malware بيخبّي الـ strings (الأوامر، الـ URLs، أسماء الـ APIs) عشان أداة strings متلاقيهاش. شوف نفس الكود C مع compilerين:

الـ floats في الـ calling conventions

System V: أول 8 floats/doubles في xmm0–xmm7 (مستقلة عن الـ integers)، وكل الـ xmm volatile، وal = عدد الـ xmm قبل الـ varargs. Windows x64: بالمكان: f(int a, double b) ← a في ecx وb في xmm1 (مش xmm0!)، والـ varargs بتتنسخ في الـ integer register كمان، وxmm6–xmm15 non-volatile — عشان كده هتلاقي movaps [rsp+…], xmm6 في prologue دوال Windows. الـ return دايمًا في xmm0.

✏️ تمارين المرحلة 16

cvttsd2si eax, xmm0 وxmm0 = -2.7. قيمة eax؟ -3 3 -2 0xFFFFFFFF الـ t = truncate = تقريب ناحية الصفر، زي (int)x في C. (cvtsd2si من غير t بيستخدم وضع التقريب الحالي = لأقرب رقم.) الـ t الزيادة في الاسم معناها إيه؟ بعد ucomisd xmm0, xmm1 وxmm0 = NaN، أنهي jump هتتنفذ؟ je — لأن ZF=1 ja jne ولا واحدة unordered ← ZF=PF=CF=1. عشان كده الـ compiler بيحط jp قبل je/jne في مقارنات المساواة. NaN بيخلي ZF وPF وCF كلهم = 1. برنامج عمل crash على movaps XMMWORD PTR [rsp+0x10], xmm0 جوه printf. السبب الأرجح؟ xmm0 فيه NaN printf مش موجودة الـ CPU مبيدعمش SSE الـ stack مكانش aligned على 16 قبل الـ call، وmovaps بتطلب عنوان مضاعف 16 ده أشهر crash لما تكتب Assembly بتنادي libc أو WinAPI: rsp لازم يبقى مضاعف 16 لحظة الـ call. الـ a في movaps = aligned. Windows x64: void f(int a, double b, int c). الـ c بتتبعت في: edx r8d — المكان التالت xmm2 على الـ stack في Windows كل argument ليه «خانة» بالترتيب: rcx/xmm0، rdx/xmm1، r8/xmm2، r9/xmm3. الـ c في الخانة التالتة وهو int ← r8d. (في System V كانت هتبقى في esi لأن الـ integers والـ floats بيتعدّوا كل نوع لوحده.) Windows بيعدّ الخانات بالمكان مش بالنوع. في sample لقيت loop فيها aesenc 9 مرات وبعدين aesenclast. ده غالبًا: anti-debug ضغط بيانات تشفير AES-128 بالهاردوير (10 جولات) — دوّر على الـ key schedule (aeskeygenassist) والمفتاح hashing بـ MD5 AES-128 = 10 rounds، ‏AES-256 = 14. وجود AES-NI في sample = تشفير حقيقي (ransomware، تشفير الاتصال بالـ C2). aes في الاسم… pcmpeqb xmm0, xmm1 (xmm1 = أصفار) ثم pmovmskb eax, xmm0 ثم bsf eax, eax. الكود ده بيحسب: مجموع الـ bytes مكان أول byte = 0 في الـ 16 byte — يعني جزء من strlen عدد الأصفار XOR للـ buffer بالظبط اللي جربته في أداة الـ SIMD: الـ mask فيه bit لكل byte صفر، وbsf بيجيب أول واحد. جرّب اختيار pcmpeqb + pmovmskb في أداة الـ SIMD فوق. 32-bit (cdecl): دالة بترجع double. الـ caller هيلاقي النتيجة فين؟ st(0) — أعلى الـ x87 stack edx:eax xmm0 على الـ stack الـ 32-bit ABIs قبل SSE: الـ floats بترجع في st(0)، فهتشوف fstp qword [ebp-8] بعد الـ call. الـ 32-bit اتصممت قبل SSE… عندك 4 درجات حرارة double في temps. لكل واحدة احسب F = C × 9 / 5 + 32 بـ SSE واطبعها كـ integer (truncate بـ cvttsd2si) في سطر لوحدها:
