الـ Calling Conventions: مين بيحط إيه وفين

عشان دالتين اتكتبوا بـ compilers مختلفة يشتغلوا مع بعض، لازم يتفقوا: الـ arguments بتتحط فين؟ النتيجة بترجع فين؟ مين بينضف الـ stack؟ مين مسؤول عن حفظ أنهي registers؟ الاتفاق ده اسمه calling convention. ومعرفته أسرع طريقة تعرف بيها عدد وقيم الـ arguments لأي دالة في الـ disassembly — وتفهم أي call لـ Windows API.

rdi وrsi: الفرق الأخطر

إزاي تعرف عدد الـ arguments لأي دالة RE workflow

01

بص على الـ callee

أي register من registers الـ args بيتقري قبل ما يتكتب فيه = argument. (Linux: rdi, rsi, rdx, rcx, r8, r9 بالترتيب؛ Windows: rcx, rdx, r8, r9، وبعدها [rsp+28h]… عند الدخول).

02

بص على الـ callers

كل الأماكن اللي بتنادي الدالة (xrefs — X في IDA): إيه اللي بيتحط في الـ registers والـ stack قبل الـ call. لو registers زيادة بتتظبط وملهاش استخدام — مش args.

03

في 32-bit: ret N وadd esp, N

ret 0Ch = stdcall بـ 3 args. ولو ret عادية وبعد الـ call add esp, 10h = cdecl بـ 4 args.

04

اتأكد من الـ return value

بعد الـ call: الـ caller بيستخدم eax/rax؟ (test eax, eax مثلًا) يبقى الدالة بترجع حاجة. لو بيكتب في rax قبل ما يقراه — void.

اكتب دالة بتحترم الـ ABI LAB

المعمل ده فيه helper بتتصرف زي دالة حقيقية: بتبوّظ كل الـ volatile registers (Linux). شوف إزاي compute بتحافظ على قيمة محتاجاها بعد الـ call — بتحطها في rbx (callee-saved) وبتحفظ rbx القديم:

compute: ; return (a * b) + c (a=rdi, b=rsi, c=rdx) push rbx ; rbx is callee-saved: keep the caller's value mov rbx, rdx ; c must survive the call -> keep it in rbx call helper ; rax = a * b (destroys rcx rdx rsi rdi r8-r11) add rax, rbx ; + c pop rbx ret helper: ; behaves like a real ABI function mov rax, rdi imul rax, rsi mov rcx, -1 ; trash every volatile register mov rdx, -1 mov rsi, -1 mov rdi, -1 mov r8, -1 mov r9, -1 mov r10, -1 mov r11, -1 ret

Windows: rcx, rdx, ثم… دالة 32-bit بتخلص بـ ret 10h. نوعها وعدد الـ args (كلها 4 bytes)؟ cdecl، 16 stdcall، 16 cdecl، 4 stdcall، 4 ret N = الـ callee بيشيل الـ args = stdcall. 0x10 = 16 byte = 4 args. ده شكل أي WinAPI زي MessageBoxA (4 args). مين اللي بينضف لما يبقى فيه رقم بعد ret؟ و0x10 بالـ decimal كام؟ على Linux، بعد call some_function، أنهي register مضمون إنه لسه بقيمته القديمة؟ rbx rcx rdi r11 rbx, rbp, r12–r15 callee-saved. الباقي volatile — ممكن يتبوّظ. دوّر على الـ callee-saved في جدول System V. دالة Windows x64 لسه داخلة (من غير أي push أو sub) وبتقرا [rsp+30h]. ده الـ argument رقم كام؟ 3 5 6 مش argument عند الدخول: [rsp] = return، [rsp+8..+20h] = shadow (args 1-4)، [rsp+28h] = arg5، [rsp+30h] = arg6. عدّ: return address (8) + shadow (32) = 40 = 0x28 → arg5. وكل arg بعده +8. xor eax, eax قبل call printf على Linux معناها: printf هترجع صفر مفيش أي argument في registers الـ xmm (عدد الـ vector args = 0) الـ format string فاضية تصفير الـ return value للدوال الـ variadic في System V، al = عدد registers الـ xmm المستخدمة. افتكر مثال varargs.c. في MSVC 32-bit لقيت دالة اسمها @Decrypt@12. ده: cdecl بـ 12 argument stdcall بـ 3 arguments C++ method fastcall بـ 12 byte arguments (أول اتنين في ecx وedx) الـ @ في الأول = fastcall، والـ @12 = حجم الـ args بالـ bytes (3 args من 4 bytes: 2 في registers وواحد على الـ stack). الـ decoration: _name = cdecl، _name@N = stdcall، @name@N = ? في 32-bit: push 0 / push offset caption / push offset text / push 0 / call MessageBoxA. الـ hWnd (أول argument) قيمته: 0 (آخر push) 0 (أول push) text caption الـ args بتتعمل push من اليمين للشمال، فآخر push = أول argument: MessageBoxA(hWnd=0, lpText=text, lpCaption=caption, uType=0). يمين ← شمال: الـ push الأخير هو الـ argument الأول. في method C++ متكومبايلة بـ MSVC 32-bit لقيت mov eax, [ecx+8] أول سطر. ecx هنا غالبًا: عدّاد loop argument عادي this (thiscall) — والسطر بيقرا field عند offset 8 في الـ object الـ return value thiscall: this في ecx. على x64 (Windows) this بيبقى في rcx لأنه أول argument. C++ methods في MSVC 32-bit ليها convention خاص. اكتب calc: بترجع sq(a) + sq(b) حيث a في rdi وb في rsi. الدالة sq جاهزة (بترجع rdi*rdi في rax) وبتبوّظ كل الـ volatile registers زي أي دالة حقيقية. لازم تحتفظ بـ b والنتيجة الوسيطة في registers آمنة، وتحافظ على أي callee-saved بتستخدمه. (والـ stack لازم يفضل متوازن!) calc: call sq ; sq(a) ... but b in rsi gets destroyed! ret sq: ; rax = rdi * rdi, trashes volatile registers mov rax, rdi imul rax, rdi mov rcx, -1 mov rdx, -1 mov rsi, -1 mov rdi, -1 mov r8, -1 mov r9, -1 mov r10, -1 mov r11, -1 ret calc: push rbx push r12 mov rbx, rsi ; keep b safe call sq ; rax = a*a mov r12, rax ; keep the partial result safe mov rdi, rbx call sq ; rax = b*b add rax, r12 pop r12 pop rbx ret sq: ; rax = rdi * rdi, trashes volatile registers mov rax, rdi imul rax, rdi mov rcx, -1 mov rdx, -1 mov rsi, -1 mov rdi, -1 mov r8, -1 mov r9, -1 mov r10, -1 mov r11, -1 ret دالة Linux x64 (gcc). بتاخد كام argument؟ mystery: lea eax, [rdi+rsi] imul eax, edx mov ecx, 10 sub eax, ecx ret دوّر على registers الـ args اللي بتتقري قبل ما تتكتب. rcx هنا اتكتب الأول. اتقري rdi وrsi وedx قبل الكتابة ← 3 args. أما ecx فاتكتب فيه (mov ecx, 10) قبل استخدامه ← متغير مؤقت مش argument. الدالة: int mystery(int a, int b, int c) { return (a + b) * c - 10; }. sample 32-bit فيه دالة اسمها مش ظاهر (resolved dynamically) اتنادت كده: 7 pushes قبلها ومفيش add esp بعدها، والـ arguments (من أول argument): handle لـ process تاني، NULL، 0، عنوان في الـ process التاني، pointer، 0، pointer لـ DWORD. أشهر WinAPI بالشكل ده بتستخدم في الـ injection؟ stdcall بـ 7 args، وأول argument handle لـ process تاني، والرابع عنوان بداية تنفيذ… CreateRemoteThread(hProcess, lpThreadAttributes, dwStackSize, lpStartAddress, lpParameter, dwCreationFlags, lpThreadId) — 7 args، stdcall (مفيش تنضيف من الـ caller). الـ lpStartAddress في الـ process التاني = غالبًا shellcode اتكتب بـ WriteProcessMemory. ده آخر خطوة في الـ classic injection (هنشوفها متحركة في مرحلة الـ shellcode).
